# 구조

이 문서는 IrisGUI 안에서 실제로 무슨 일이 벌어지는지 다룹니다. 봇 개발에 필요한
바깥 동작만 이해하려면 [API 동작 상세](03-apis.md)만으로도 충분하지만, 문제 진단이나
직접 서버를 만들 땐 내부 흐름이 도움이 됩니다.

## 프로세스 모델

IrisGUI는 하나의 APK가 두 가지 역할을 맡습니다.

| 역할 | 실행 위치 | 하는 일 |
|---|---|---|
| 관리 앱 | 안드로이드 앱 프로세스 | 화면, 설정 저장, 권한 처리, 모드 제어 |
| 백그라운드 서버 | ROOT_ADB 모드: 루트 권한 별도 프로세스<br>NON_ROOT 모드: 앱 프로세스 내부 | 이벤트 수집, HTTP/WebSocket 서버 운영, 답장 발송 |

ROOT_ADB 모드에서는 카톡 데이터베이스에 접근하려면 루트 권한이 필요하기 때문에,
서버 로직을 앱 밖 별도 프로세스(`app_process`)로 분리합니다. 앱 화면은 이 서버의
상태를 주기적으로 조회하고 시작/정지를 제어하는 감시자 역할만 합니다.

NON_ROOT 모드에서는 루트가 필요 없으므로 서버가 앱 안에서 그대로 동작합니다.
대신 DB 접근이 불가해 API가 `/ws`, `/reply` 두 개뿐입니다.

HAYUL 모드는 HayulGUI 패치로 카카오톡과 같은 사용자 ID를 공유하기 때문에, 루트 없이
DB를 직접 읽고 서버는 앱 안에서 돌립니다 — ROOT_ADB와 NON_ROOT의 절충형입니다.

## 이벤트 흐름 — 루팅 계열(ROOT_ADB · HAYUL)

```
카카오톡 DB(chat_logs)
   │  주기적으로 "마지막으로 본 id 이후 새 행"을 질의 (기본 100ms마다)
   ▼
새 행 발견 → 복호화 (message, attachment, supplement)
   │
   ▼
방 이름 / 보낸이 이름을 DB에서 해석
   │
   ▼
이벤트 생성: { msg, room, sender, json: <원본 행 전부> }
   ├─▶ WebSocket /ws 접속자에게 브로드캐스트
   └─▶ webEndpoint가 설정돼 있으면 HTTP POST
```

여기서 눈여겨볼 점:

- **중복 없음** — 루팅 모드에서는 DB를 이벤트의 유일한 출처로 삼습니다. 알림까지 읽으면
  같은 메시지가 두 번 갈 수 있어 의도적으로 알림 이벤트를 켜 두지 않습니다.
- **되풀이 전송 없음** — `SYNCMSG`, `MCHATLOGS`처럼 과거 내용을 다시 끌어오는 타입은
  이벤트로 내보내지 않습니다. 새 메시지나 명백한 변경만 전달됩니다.
- **extension 필드** — 기본은 위 형식 그대로이며, `POST /config/extension {enable:true}`를
  하면 타입 코드, 리액션, 삭제 여부 같은 확장 정보가 top-level `extension`으로 추가됩니다.

## 이벤트 흐름 — NON_ROOT

```
카카오톡 알림
   │  알림 리스너 서비스(NLS)가 수신
   ▼
알림에서 추출: 발신이름, 본문, 방 이름, 방 id, 메시지 id, 프로필 이미지
   ▼
이벤트 생성: { msg, room, sender, is_group_chat, profile_image, json: {…} }
   ├─▶ WebSocket /ws 브로드캐스트
   └─▶ webEndpoint HTTP POST
```

알림에서 알 수 있는 것이 곧 이벤트의 전부이므로, 루팅 모드와는 json 필드의
풍성함이 다릅니다. 자세한 비교표는 [API 동작 상세](03-apis.md)에 있습니다.

## 답장 흐름

`POST /reply`를 받으면 IrisGUI는 즉시 "Enqueued"(큐에 등록됨)라는 응답만 보내고, 실제 발송은
큐에서 순차적으로 처리합니다. 즉 발송 성공 여부는 이 응답에 담기지 않으며,
속도가 느려도 요청이 막히지 않는 방식입니다.

| 모드 | 발송 방식 |
|---|---|
| ROOT_ADB / HAYUL | 카카오톡 내부 서비스와 액티비티에 직접 전달. 시스템 내장 API를 이용하므로 별도 설정 없이 텍스트와 첨부가 모두 가능 |
| NON_ROOT | 알림에서 수집한 답장용 PendingIntent를 재활용. 첨부는 이미지 공유(sharing)으로 전달 |

텍스트는 `message_send_rate`(기본 50ms)만큼 간격을 두고 순서대로 나가므로,
한 번에 많은 방으로 뿌려도 카카오톡에 과부하가 걸리지 않습니다.

## 두 개의 HTTP 서버

| 서버 | 위치 | 모드 | 노출 API |
|---|---|---|---|
| IrisServer | 앱 내부 | NON_ROOT | `/ws`, `/reply` |
| AdbServer | 별도 프로세스 | ROOT_ADB | `/ws`, `/reply` + 조회·검색·설정 계열 전부 |

(HAYUL 모드에서는 AdbServer와 같은 구성이 앱 안에서 동작합니다.)

둘 모두 JSON을 다룰 때 모르는 키는 조용히 무시하므로, 요청 메시지에 쓸데없는 필드가
섞여도 문제 없이 처리됩니다.

## 앱 안의 스크립트 환경

ROOT_ADB 모드는 기기 안에 우분투 기반의 작은 Linux(userland)를 갖고, 여기서 Python
프로젝트를 돌려 이벤트 스트림을 바로 소비할 수 있습니다. 구조는
[스크립트 · Linux 환경](05-script-linux.md)을 참고하세요.

## 설정 저장

- 앱은 SharedPreferences에 저장하지만, 루트 서버는 별도 프로세스라 JSON 파일로
  공유합니다. 서버가 시작되면 이 JSON을 읽어 앱 화면 표시 값과 동기화합니다.
- 포트만 유일하게 즉시 반영되지 않습니다. UI에서 바꾸면 서버는 다음 시작부터
  바뀐 포트를 사용하므로, 변경 후 반드시 재시작해야 합니다.

## 장애 복구

- 앱은 전경(foreground) 서비스와 watchdog 타이머로 항상 살아 있으려 시도합니다.
- 재시작 계기: 부팅 완료, 앱 업데이트, 15분 주기 heartbeat.
- 루트 서버도 백그라운드에 분리된 상태로 살아남아, 터미널 연결을 끊어도
  계속 동작합니다.
